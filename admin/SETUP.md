# ハモソ管理画面：認証APIの設定手順

## 目的と現在の範囲
このWorkerは年度共通パスワードをサーバー側で照合し、署名付きセッショントークンを発行します。ログイン試行はIPごとに15分で最大5回までに制限します。お知らせ・演奏会情報、画像アップロード、サイト情報（活動紹介・写真URL・動画URL・SNS・入会案内・活動予定）の管理APIを含みます。

## Cloudflare側の設定（ブラウザのみ）
1. Cloudflareアカウントを作成し、Workers & Pagesから新しいWorkerを作成します。
2. このリポジトリの `admin/worker.js` の内容をWorkerのコードエディターに貼り付けて保存・デプロイします。
3. WorkerのSettings / Bindingsで、KV namespaceを作成し、変数名 `LOGIN_LIMITS` でバインドします。
4. WorkerのSettings / Variables and Secretsで、次の2つを **Secret** として登録します（通常のText変数ではなくSecret）。
   - `ADMIN_PASSWORD`: 年度用の強いパスワード。長くランダムなもの（推奨20文字以上）にし、チャットやリポジトリに書かないでください。
   - `SESSION_SECRET`: 別のランダムな秘密値。少なくとも32文字。通常の年度更新では、管理画面のパスワード変更により既存セッションが無効になります。
5. WorkerのURL（例：`https://任意の名前.あなたのサブドメイン.workers.dev`）を控えます。実際のURLはCloudflareが発行したものを使います。

## 既存Workerのコードを更新する場合（ブラウザのみ）
既に稼働しているWorkerを更新するときは、新しいWorkerを作らず、現在のWorkerを更新します。管理画面のAPI URLが変わらないようにするためです。

1. GitHubで対象PRがmainに反映され、必要な自動検査が成功したことを確認します。
2. GitHubのmainブランチで `admin/worker.js` を開き、ファイル全体をコピーします。複数のWorker変更PRがある場合は、すべてmainに反映された後の最新版を使います。
3. Cloudflare DashboardのWorkers & Pagesから、現在使っている `hamoso-admin-auth` Workerを開き、コード編集画面に進みます。
4. 既存コード全体をmainの `admin/worker.js` に置き換え、保存・Deployします。新しいWorkerを作成したり、Worker名・workers.dev URLを変更したりしません。
5. Settings / Bindingsで既存のKV binding `LOGIN_LIMITS` が残っていることを確認します。Settings / Variables and Secretsで `ADMIN_PASSWORD` と `SESSION_SECRET` が設定済みであることも確認します。コード更新だけならSecretの値を変更する必要はありません。
6. デプロイ後、管理画面でログイン、セッション確認、サイト情報の読み込み、お知らせ、画像、バックアップを確認します。パスワード変更を初めて試す場合は、変更後に全端末がログアウトされることを前提に、現役担当者への共有準備を済ませてから行います。
7. 異常があればCloudflareの直前の正常なWorkerバージョンへ戻します。KVのコンテンツやSecretを原因調査のために削除しないでください。

**注意：** GitHub Pagesの公開が成功してもWorkerは自動更新されません。PR #53のパスワード変更やPR #64の画像ライブラリなど、Workerコードを変更する機能は、main反映後にこの手順でWorkerを再デプロイするまで利用できません。

## 画像の保存・削除
- 管理画面からアップロードした画像は、ブラウザで再エンコードしてから保存します。通常のJPEG / PNG / WebPに含まれるEXIF等のメタデータは、再エンコード時に引き継がれません。
- 新規画像は期限なしでKVに保存し、管理画面の「保存画像を完全削除」から明示的に削除します。削除すると活動写真・お知らせの参照も自動で外れます。
- 旧仕様で保存された画像には1年間のTTLが残っている場合があります。サイト情報・写真管理画面の「既存画像の保存期限を延長」を一度実行すると、既存画像も期限なしに切り替わります。
- リポジトリ内にある静的画像ファイルは、このWorkerの画像ストレージとは別管理です。

## お知らせ・年度別アーカイブ
- お知らせの保存・公開APIの上限を2,000件（JSONデータ10MB）に拡張しました。公開APIは公開中の記事を日付順に最大2,000件返し、年度別アーカイブが年度ごとに絞り込みます。
- 旧仕様の上限50件でKVに保存されなかった過去記事は、この変更だけでは復元されません。旧サイト・旧データ・手元の原稿などからの移行が必要です。現時点のKV内記事数・欠落状況は本番データを確認するまで断定しません。

## GitHub運用・ブランチ保護
- `.github/workflows/site-quality.yml` はPull RequestとmainへのpushでHTML・サイトマップ・ローカル参照・OGP・画像alt・ID重複・JavaScript構文を自動検査します。
- `main`の直接pushを防ぐには、GitHubのSettings → Branches → Add branch protection ruleで`main`を対象にし、Pull Request必須、Status checks必須（`site-audit`）、force push禁止、branch deletion禁止を有効にしてください。
- このGitHub接続ではブランチ保護ルールを書き込む権限がないため、ルール自体は管理画面での設定が必要です。設定後はPR画面で`site-audit`が成功するまでマージしない運用にしてください。

## Search Console・robots.txt
- このサイトはGitHub Pagesのプロジェクトサイト形式で、公開URLに `/Meiji-HarmonicaSociety-website/` が含まれます。そのため、このリポジトリ直下の `robots.txt` は `https://hamosositemeiji.github.io/Meiji-HarmonicaSociety-website/robots.txt` に配置され、ホスト直下の `https://hamosositemeiji.github.io/robots.txt` にはなりません。
- Googleのrobots.txt仕様では、robots.txtは対象ホストのルートに置く必要があります。プロジェクトサイト内のrobots.txtはGoogleのホスト全体向けクロール制御としては機能しません。
- 現在のサイトマップは `https://hamosositemeiji.github.io/Meiji-HarmonicaSociety-website/sitemap.xml` です。Search Consoleでは、URLプレフィックスプロパティを `https://hamosositemeiji.github.io/Meiji-HarmonicaSociety-website/` に合わせ、そのプロパティの「サイトマップ」から上記の完全URLを直接送信してください。
- `Couldn't fetch` の原因はrobots.txtの配置だけでは断定できません。公開後にブラウザでサイトマップURLがHTTP 200で取得できること、XMLが正しいこと、Search ConsoleのプロパティURLが一致していることを個別に確認してください。
- ホスト直下のrobots.txtが必要な場合は、`hamosositemeiji.github.io` というユーザーサイト用リポジトリを別途用意するか、独自ドメインを設定する必要があります。現時点では既存のユーザーサイト用リポジトリが確認できなかったため、新規作成はしていません。

## バックアップと復元
- 管理画面トップの「データのバックアップ・復元」から、サイト情報・お知らせ・アップロード画像を1つのJSONファイルに書き出せます。
- バックアップは運営担当者が定期的にダウンロードし、アクセス制限された安全な場所に保管してください。ファイルには公開予定の部員情報・画像も含まれるため、公開リポジトリや共有リンクに置かないでください。
- 復元はバックアップ内の画像を先に登録し、サイト情報・お知らせを最後に置き換えます。既存の画像データは自動削除せず、バックアップに含まれない画像は残します。
- サイト情報・お知らせの保存前には直前のデータをKV内に90日間保存し、各種類の直近20件を保持します。
- 同じデータを複数の管理画面で編集した場合、古い画面からの保存はrevision conflictとして拒否します。Cloudflare KVには原子的なcompare-and-swapがないため、同時刻に重なった保存を完全に直列化するものではありません。複数人で同時編集せず、保存担当を1人に決めてください。

## 旧CMS設定について
- `admin/config.yml` はDecap CMS / Git Gatewayを想定した旧設定で、現行管理画面では読み込まれていません。
- `content/site.json` は旧CMS時代の参考データです。現行サイトの活動予定・コンテンツはCloudflare KVの `content:site-content` が保存先です。
- 旧JSONを編集しても現行サイトには反映されません。移行元の記録として残し、削除・上書きしないでください。

## 年度更新・パスワード変更
- 通常の年度更新では、管理画面トップの「パスワード変更」から実施します。現在のパスワードを確認したうえで12文字以上の新しいパスワードを設定します。
- パスワードはPBKDF2-SHA-256でハッシュ化してKVに保存し、平文では保存しません。変更時には全ログインセッションを無効化し、全端末で再ログインが必要になります。
- 初回導入時は従来どおりWorker Secretの `ADMIN_PASSWORD` が初期パスワードとして使われます。管理画面から一度変更すると、KVのハッシュが優先され、Secretの値ではログインできなくなります。
- パスワードを忘れた場合の緊急復旧は、Cloudflare KVの `auth:password-hash` を削除すると、Worker Secretの `ADMIN_PASSWORD` が再び初期パスワードとして有効になります。その後、管理画面から新しいパスワードを設定してください。この操作は通常の年度更新では不要です。
- 新パスワードは別経路で現役運営メンバーに共有し、退任者に共有しないでください。パスワードや秘密値をGitHubやチャットに記載しないでください。

## 年度引き継ぎの標準手順
対応する本番Workerでログイン・バックアップ・パスワード変更が使えることを確認してから始めます。通常の年度交代は管理画面で行えます。管理画面トップの「新年度への引き継ぎ」も参照してください。

1. 旧担当者が管理画面から最新バックアップJSONをダウンロードし、アクセス制限された保管先に保存します。
2. 「役員・お問い合わせ先」で役員とサイト管理者を更新します。役員とサイト管理者は別枠です。サイト作成者は固定情報なので変更しません。役員・サイト管理者の氏名やメールアドレスは公開APIにも出るため、保存前に本人の掲載同意を確認します。
3. 「活動・年間予定」で定例練習、活動場所、年間予定を更新します。
4. 「入会・見学案内」で新年度の活動日時・参加方法・問い合わせURLを確認し、「演奏動画・SNS」で公式SNSを確認します。手順2〜4の変更は画面下部の「変更を保存」を押し、保存完了を確認します。
5. 「お知らせ・演奏会情報」で古い告知は「公開サイトに掲載する」のチェックを外し、新年度の告知を追加します。「一覧に追加・更新」を押し、「変更を保存」で保存完了を確認します。
6. 「パスワード変更」で管理者パスワードを変更します。現在のパスワードを入力し、12文字以上の新しいパスワードを設定して、現役担当者だけに安全な方法で共有します。変更すると全端末がログアウトされます。
7. ログインし直し、スマートフォンとPCでトップページ、活動紹介、見学案内、役員・連絡先、活動予定、お知らせ、写真、SNSリンクを確認します。
8. 更新後のバックアップもダウンロードし、旧バックアップと区別して保管します。

通常の年度更新でCloudflareやGitHubを操作する必要はありません。管理画面の機能追加・修正など、Workerのソースコードを変更した場合だけ、GitHubへの反映とは別にCloudflare Workerの再デプロイが必要です。

## 注意
- Workerのソースコードは公開リポジトリに置いても構いませんが、パスワード、セッション秘密値、APIトークンは絶対に書き込まないでください。
- `admin/worker.js` を更新した場合は、Cloudflare DashboardからWorkerのコードを最新内容に置き換えて再デプロイしてください。GitHubへのコミットだけではCloudflare上のWorkerは更新されません。
- `admin/site-content.html` の保存先はKVの管理用領域です。公開サイトへの反映は公開読み出しAPIとサイト側の表示処理に依存します。保存後は公開ページで表示を確認してください。
- 問い合わせは公式サイトに掲載している連絡先へのメールで受け付けます。管理画面内に問い合わせ受信箱はありません。
- Cloudflareの無料枠・仕様は変更されることがあります。最新の制限は公式ドキュメントを確認してください。
